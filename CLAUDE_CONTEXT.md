# CLAUDE_CONTEXT.md

Guidance for AI coding sessions on **CharSayWhat**. Read this before writing code.

---

## 1. What this project is

CharSayWhat tells you exactly what characters are in a string. It exists because
reading a password character-by-character off a screen is miserable: is that a
`0` or an `O`, an `l` or a `1`, a trailing space or nothing at all?

Everything that follows serves that one goal. When a design question is close,
the tie-breaker is **"does this help someone decypher an ambiguous string?"**

## 2. Tech stack

| Thing | Value |
|---|---|
| Language | Go **1.23.8** (`go.mod`) |
| Module | `charsaywhat` |
| Package | single flat `package main` at repo root |
| GUI (Windows) | `github.com/jchv/go-webview2` — embedded HTML/CSS/JS page |
| GUI (non-Windows) | `gioui.org v0.9.0` — immediate-mode native UI |
| Database | **none** — no persistence, no state, no config file, no network |
| Test framework | stdlib `testing` — `main_test.go` (see §7) |

There is **no `package.json`** — this is not a Node project. The HTML/CSS/JS in
`gui_windows.go` is a Go string constant, not a web app. No npm, no bundler, no
frontend build step.

### Dependency policy

**Standard library only. Do not add Go modules.** The two GUI libraries above
are the entire dependency budget; treat it as closed. If a task seems to need a
new dependency, stop and ask before adding it.

> **`github.com/go-text/typesetting` is pinned to v0.3.0** — the version Gio
> v0.9.0 declares. At v0.3.4 (what the original commit had) every rune shapes
> to the `.notdef` glyph and the Gio GUI shows only empty boxes.
> `TestShaperFindsGlyphs` (`gui_test.go`) guards this; don't bump typesetting
> independently of Gio.
>
> `go mod tidy` considers every platform's build tags, so running it on Linux
> keeps the Windows-only `go-webview2` dependency. Both GUI libraries are in the
> direct require block.

Flat by design. **Keep it flat** — do not introduce `internal/`, `pkg/`, or
sub-packages unless the file count genuinely demands it.

```

main_test.go          table-driven tests for the pure core
gui_test.go           //go:build !windows   -> Gio font-shaping, fitWidths and icon tests
gui_icon.go           //go:build !windows   -> embeds icons/*.png, builds _NET_WM_ICON data
gui_icon_x11.go       //go:build linux && !nox11  -> cgo/Xlib: sets _NET_WM_ICON on the window
gui_icon_other.go     //go:build !windows && (!linux || nox11) -> setWindowIcon no-op
icons/                charsaywhat-{16..256}.png, generated by `./build.sh icons` (committed;
                      the Linux build embeds them, so it fails without them)
charsaywhat.desktop   launcher installed by `./build.sh install`
gui.go                //go:build !windows   -> Gio GUI
gui_windows.go        //go:build windows    -> WebView2 GUI (embedded HTML)
console_windows.go    //go:build windows    -> prepareGUI(): hide/detach console before GUI
console_other.go      //go:build !windows   -> prepareGUI() returns true
icon_windows.go       //go:build windows    -> sets window icon from the .exe
build.ps1             Windows build script        -> bin\charsaywhat.exe
build.sh              Linux build script          -> bin/charsaywhat (+ Windows cross-compile)
make_ico.ps1          generates charsaywhat.ico from charsaywhat.png
charsaywhat.png/.ico  icon source / generated icon (committed)
rsrc_windows_amd64.syso   compiled icon resource (generated, committed)
bin/                  build output; gitignored except charsaywhat.exe (see §8)
```

### The build-tag pattern

Platform-specific behaviour is split into paired files with `//go:build` tags,
never `runtime.GOOS` checks inside a function. Every `//go:build windows` file
has a `//go:build !windows` partner exposing the **same function signature**.

If you add a platform-specific capability, follow this exact shape: declare the
function in both files, give the non-Windows side a working fallback or a no-op.
A missing partner file breaks the Linux build, and that build must keep working
(see §5).

## 4. Architecture

### Entry dispatch (`main.go`, `func main`)

One binary, chosen at startup:

1. **No args and stdin not piped** -> `if prepareGUI() { runGUI() }`
2. **Otherwise** -> `parseArgs(os.Args[1:])`:
   - `-h`/`--help` -> print `usage`
   - text args present -> `runCLI(strings.Join(text, " "), names)`
   - no text but stdin piped (`isPiped()`) -> read all lines, `runCLI`
   - no text and nothing piped (e.g. bare `-s`) -> usage to stderr, exit 2

### CLI switches

`parseArgs` is a small hand-written parser, deliberately **not** `flag`:

- `-s` -> `symbolNames` (type shown as an example char: `a A 9 $ .`, space as a
  blank, plus `\n`, `\t`, `?` for newline/tab/other)
- `-c` -> `codeNames` (`lc uc di sp sy pu`, plus `nl tb ot`)
- `-s` with `-c` is an error (exit 2).
- `--` ends switches. Parsing also stops at the **first argument that isn't
  exactly a known switch**, and that argument and everything after it is text.
  So `charsaywhat -x1` analyses `-x1` and `charsaywhat abc -s` analyses
  `abc -s`. This is intentional: passwords often start with `-`, and rejecting
  them as unknown flags would be hostile. Keep this behaviour.

Short naming is applied in `runCLI` by remapping `charInfo.typ` *after*
`analyzeText`; `analyzeText` always returns full names because the WebView2 CSS
classes key off them. The switches are CLI-only — the GUIs always show full
names. The user's spec for `-s`/`-c` only covered six types; newline/tab/other
mappings were filled in by Claude and may be revisited.

### Windows console handling — do not link with `-H windowsgui`

The Windows exe is a normal **console-subsystem** binary. It used to be
`-H windowsgui` plus `AttachConsole(ATTACH_PARENT_PROCESS)`, but shells don't
wait for GUI-subsystem processes: PowerShell printed its next prompt
immediately and the CLI output got interleaved with / eaten by the next
command (cmd.exe usually won the race by luck). Don't go back to that.

Instead, `prepareGUI()` (`console_windows.go`) runs only on the GUI path and
uses `GetConsoleProcessList` to decide:

- **0 processes** — no console (the detached relaunch) -> run the GUI.
- **1 process** — Windows created a console just for us (double-click in
  Explorer, shortcut) -> `FreeConsole()` and run the GUI. A console window
  flashes briefly on launch; that's the accepted cost of this approach.
- **>1** — the console is shared with a shell -> relaunch the exe with
  `DETACHED_PROCESS | CREATE_NEW_PROCESS_GROUP` and return `false` so the
  parent exits and the prompt comes straight back. If the relaunch fails it
  falls back to running the GUI in place.

The CLI path needs no special handling — the console is already ours.

### The data model

```go
type charInfo struct {
    pos  string   // 1-based position, pre-formatted
    char string   // display form (see displayRune)
    typ  string   // classification (see classifyRune)
}
```

All three fields are **strings**, pre-formatted at analysis time. `analyzeText`
returns `[]charInfo` and the renderers only lay it out. Keep that separation:
analysis produces strings, renderers never re-derive meaning from them.

### Rendering: a column-per-character grid

All three surfaces render the same shape — characters across, three labelled
rows down:

```
Pos    1  2  3
Char   P  @  5
Type   up pu di
```

- **CLI** (`runCLI`, `main.go`): gets per-column widths from the shared
  `columnWidths` helper, then prints three rows padded to those widths.
- **Gio** (`gui.go`): a real grid drawn to match the WebView2 page: same dark
  palette, input pane with a 2dp `#007acc` rule, then a horizontally scrolling
  `widget.List` of columns (label column + one per character). Each cell is a
  bordered `gridCell`; type labels are colour-coded from `typeColors`.
  Column sizing mimics the browser's automatic table layout, which is what
  the WebView2 page really gets (`table-layout:fixed` without a table width
  falls back to auto): `fitGrid` measures each column's preferred width
  (`max(56dp, widest cell)`) and minimum (its Pos/Char text), and
  `fitWidths` water-fills to the window width, capping the widest columns
  first. Type names then wrap (`WrapGraphemes`) and the Type row grows to the
  tallest one. The grid scrolls sideways only when every column is at its
  minimum. `fitWidths` is pure and tested in `gui_test.go`.

`columnWidths` (CLI only now) counts **characters** (`utf8.RuneCountInString`), not bytes, and
padding is done by hand with `strings.Repeat` rather than `%-*s` (which pads by
bytes). Don't reintroduce `len()` or `%-*s` for grid alignment — a multi-byte
rune like `é` or `€` would misalign every column after it.
- **WebView2** (`gui_windows.go`): a `<table>` with `table-layout:fixed`; CSS
  handles alignment, so no width maths. Type cells get a CSS class equal to the
  type name for colour-coding.

New information about a character should become a **new row** in this grid, not
a new layout.

### WebView2 specifics

`gui_windows.go` holds the whole page in the `htmlPage` const: dark VS Code-ish
palette (`#1e1e1e` bg, `#d4d4d4` fg), `<textarea id="input">` on top (40% height),
`<div id="output">` below. Re-renders on every `input` event. All user text goes
through `esc()` before reaching `innerHTML`.

**Keep `esc()` on every interpolation.** The input is arbitrary pasted text —
frequently passwords — and unescaped `innerHTML` is an injection hole. Prefer
`textContent` where you don't need markup.

## 5. Platform parity contract

**Decision: full parity on both platforms.** A GUI feature is not done until it
works equivalently in the WebView2 page *and* the Gio UI, and in the CLI where
it makes sense.

The Gio path is not decorative. Keep it compiling and functional on every
change. It must present the same information **and look the same**: the user
explicitly asked for the Linux GUI to match the Windows one (table, single
scrolling line, dark background, colour-coded types).

The palette is duplicated: CSS in `htmlPage` and Go vars at the top of
`gui.go` (`colBg`, `colFg`, … `typeColors`). Change one, change the other.

Known Gio-only rough edges: a tab typed into the input box renders as a box
glyph (Gio's editor has no tab rendering; the grid still shows `[tb]`), and the
grid's text isn't selectable.

## 6. Known divergences — fix these, don't propagate them

The character logic is implemented **twice**: once in Go (`classifyRune`,
`displayRune` in `main.go`) and once in JavaScript (`classify`, `display` in
`gui_windows.go`). The copies have drifted. Both are compiled into the Windows
binary, so the exe does not arbitrate between them.

### 6a. Position semantics — FIXED (2026-10-14)

`analyzeText` used to range over the string's bytes, so `"héllo"` reported
positions `1,2,4,5,6`. It now ranges over `[]rune(s)` and matches the JS
(`[...text]`): positions count characters. `TestAnalyzeText` covers this with
multi-byte input — keep it that way.

### 6b. Display tokens disagree

| Rune | Go (`displayRune`) | JS (`display`) |
|---|---|---|
| space | `[sp]` | `" "` (invisible) |
| newline | `[nl]` | `\n` |
| tab | `[tb]` | `\t` |

**Recommended resolution: Go's bracketed tokens win, everywhere.** An invisible
space in the output defeats the entire purpose of the tool — a trailing space in
a password is exactly the thing a user is here to find. *Confirm this before
changing the Windows GUI's appearance, since it alters what you see day to day.*

### 6c. Keeping them in sync

Until the duplication is removed, **any change to classification or display must
land in both the Go and the JS copy in the same commit.** The classification
vocabulary is a closed set shared by both, and the WebView2 CSS keys off it:

`lowercase`, `uppercase`, `digit`, `space`, `newline`, `tab`, `punctuation`,
`symbol`, `other`

Adding a type means updating: `classifyRune` (Go), `classify` (JS), the CSS
colour block in `htmlPage`, `symbolNames` and `codeNames` (enforced by
`TestShortNamesCoverAllTypes`), the README type table, and `typeColors` in
`gui.go`.

> The cleanest long-term fix is to make Go the single source of truth and feed
> analyzed data to the WebView2 page through a binding, deleting the JS copy.
> Worth proposing when classification work next comes up.

## 7. Coding conventions

- **`gofmt`** — tabs, standard Go formatting. Non-negotiable.
- **Section banners** separate concerns within a file:
  ```go
  // ── shared ──────────────────────────────────────────────────────────────────
  ```
  Box-drawing `─`, padded to roughly 78 columns. Match this when adding sections.
- **Short, lowercase helper names**: `imax`, `isPiped`, `esc`. Unexported unless
  there's a reason. The codebase prefers a tiny local helper over a dependency.
- **Closures for repeated local work**: `printRow` in `runCLI`, `row` in
  `labelColumn` and `cellText` in `charColumn` are defined inline where used rather than hoisted to package
  scope. Follow this for logic used once within a function.
- **Errors**: this is a small desktop tool, not a service. Current style is to
  fail quietly and keep the UI alive (`setWindowIconFromExe` returns silently on
  every error; `runGUI` returns if webview is nil). CLI errors go to `os.Stderr`
  with `os.Exit(1)`. Don't introduce a logging framework.
- **Win32 calls**: `syscall.NewLazyDLL` + `NewProc`, with constants declared as
  untyped consts near the top (`wmSetIcon = 0x0080`). Always check the error
  return of `UTF16PtrFromString`. Keep these confined to `*_windows.go`.

### Testing

**New logic gets tests.** `main_test.go` covers `classifyRune`, `displayRune`,
`analyzeText`, `columnWidths`, `parseArgs` and the short-name maps; extend it alongside any change to them.

- Table-driven, stdlib `testing`, no assertion library.
- Test the pure core — `classifyRune`, `displayRune`, `analyzeText`, and any new
  formatting or parsing helper. Don't try to test the GUI event loops.
- Name files `foo_test.go` beside the code, same flat package.
- Run with `go test ./...`. On a Linux box missing Gio's X11/Vulkan headers,
  use `go test -tags "novulkan nox11" ./...` (see §8).
- Non-ASCII cases are mandatory given §6a: include multi-byte input in any test
  touching positions.

## 8. Building and running

All build output goes to **`bin/`**, which is gitignored **except
`bin/charsaywhat.exe`** (user decision, 2026-10-14). The Windows binary is
committed so Windows users can grab it without a Go toolchain; when you change
behaviour, rebuild it (`./build.sh windows` works from Linux) and commit it
with the source. The Linux binary stays uncommitted — it depends on system
libraries and is built per machine.

### Windows

```powershell
.\build.ps1          # -> bin\charsaywhat.exe
.\build.ps1 -Icon    # also regenerate charsaywhat.ico + rsrc_windows_amd64.syso
```

The plain build reuses the committed `rsrc_windows_amd64.syso`, so it only needs
Go. `-Icon` runs `make_ico.ps1` (PNG -> ICO via System.Drawing) and then `rsrc`,
looked up on `PATH` then in `$(go env GOPATH)\bin`
(`go install github.com/akavel/rsrc@latest`). Deliberately **not** linked
with `-H windowsgui` — see §4 "Windows console handling".

### Linux

```bash
./build.sh install    # build + install to ~/.local (PREFIX=... to change)
./build.sh icons      # regenerate icons/*.png from charsaywhat.png (ImageMagick)
./build.sh            # native Gio build        -> bin/charsaywhat
./build.sh windows    # cross-compile (no cgo)  -> bin/charsaywhat.exe
./build.sh all        # both
TAGS="novulkan nox11" ./build.sh   # reduced Gio build (Wayland only, no Vulkan)
```

The native build needs cgo plus Gio's system headers (listed at the top of
`build.sh`). The Windows cross-compile is pure Go and picks up the committed
`.syso`, so the icon is embedded even when built from Linux.

### Usage

```bash
charsaywhat                     # GUI
charsaywhat "P@ssw0rd"          # CLI, args
echo "P@ssw0rd" | charsaywhat   # CLI, piped
charsaywhat -s "P@ssw0rd"       # CLI, example-char type names
charsaywhat -c "P@ssw0rd"       # CLI, two-letter type codes
charsaywhat -- -s               # CLI, text that looks like a switch
```

## 9. Checklist for a new feature

1. Does it serve "help me decypher this string"? (§1)
2. Does it touch classification or display? -> update **both** Go and JS copies,
   plus the CSS class list. (§6c)
3. Does it change the GUI? -> implement in **both** WebView2 and Gio. (§5)
4. Does it add platform-specific code? -> paired `//go:build` files with
   matching signatures. (§3)
5. Is there new pure logic? -> table-driven tests, including non-ASCII. (§7)
6. Does it need a new dependency? -> **stop and ask.** (§2)
7. Does user text reach `innerHTML`? -> it goes through `esc()`. (§4)
8. `go test ./...` passes and both `build.ps1` / `build.sh` still build. (§8)
